# Риски и требования безопасности

Проект: **«Разбор жалоб на контент»**. Основа: [паспорт проекта](PROJECT.md), OWASP Top 10:2025 и OWASP ASVS 5.0.0. Это проектные риски и требования к будущей реализации, а не результаты проверки работающего сервера. [Угрозы и приоритеты](THREAT_MODEL.md) и [решения с будущими проверками](DESIGN_DECISIONS.md) уточняют реализацию этих свойств. Продукт — REST API с локальной SQLite-базой, подготовленными учебными аккаунтами и каталогом материалов; отдельного пользовательского интерфейса, загрузки файлов и внешних интеграций нет.

## Риски по OWASP Top 10:2025

| Категория | Сценарий риска в проекте и последствия |
| --- | --- |
| **A01 Broken Access Control** | Пользователь подставляет ID чужой жалобы в запрос просмотра и узнаёт автора и причину обращения; либо вызывает действие модератора и скрывает материал без полномочий. |
| **A02 Security Misconfiguration** | При запуске API вне локальной разработки остаются включены отладочный режим или служебные `/docs` и `/openapi.json`, если они предназначены только для команды. Посторонний получает сведения о внутренних маршрутах или диагностике. |
| **A03 Software Supply Chain Failures** | При сборке устанавливается подменённая либо уязвимая версия FastAPI, SQLAlchemy или другой зависимости из незафиксированного источника. Она получает доступ к аккаунтам, жалобам и решениям в процессе сервера. |
| **A04 Cryptographic Failures** | Пароли заранее созданных аккаунтов сохраняются в SQLite или исходных данных открытым текстом либо быстрым хешем. Утечка файла базы позволяет восстановить пароль модератора и действовать от его имени. |
| **A05 Injection** | Причина жалобы или параметр фильтра попадает в SQL-запрос как часть строки. Атакующий меняет запрос и читает чужие жалобы либо изменяет данные. |
| **A06 Insecure Design** | Два модератора одновременно рассматривают одну ожидающую жалобу. Без правила единственного перехода оба решения сохраняются, а статус жалобы и состояние материала расходятся. |
| **A07 Authentication Failures** | Для входа в заранее созданный аккаунт модератора можно неограниченно подбирать пароль. После успешного подбора злоумышленник получает право решать жалобы и скрывать материалы. |
| **A08 Software or Data Integrity Failures** | При первоначальном или повторном заполнении базы приложение принимает недопустимое начальное состояние либо перезаписывает уже скрытый материал исходным `visible`. Для текущего проекта источник каталога — версионируемый код; внешний файл не импортируется. Компрометация самого кода относится также к A03. |
| **A09 Security Logging and Alerting Failures** | Решение модератора меняет состояние материала, но приложение не фиксирует исполнителя, жалобу, время и результат. Позже невозможно установить источник неправомерного скрытия; повторные отказы в доступе и попытки входа остаются незамеченными. |
| **A10 Mishandling of Exceptional Conditions** | После записи решения возникает ошибка при скрытии материала или фиксации статуса жалобы. API возвращает ошибку, но частичные изменения остаются в базе: жалоба удовлетворена, а материал всё ещё доступен, либо наоборот. |

## Требования безопасности

`SR-*` задают обязательное свойство и критерий приёмки. Ссылки ASVS указывают на применимые пункты стандарта и не утверждают соответствие всему уровню ASVS. Для каждого критерия проверяется также состояние базы после отказа или ошибки.

| ID | Требование | Критерий приёмки | Связь с OWASP |
| --- | --- | --- | --- |
| **SR-01** <a id="sr-01"></a> | API разрешает пользователю читать только собственные жалобы; решение по жалобе и скрытие материала доступны только модератору. Сервер проверяет роль и право на выбранный объект при каждом запросе; личность и роль берёт из проверенного серверного контекста, а не из клиентских полей. Без действующего контекста доступ к жалобам и решениям запрещён. Общедоступный каталог исключает скрытые материалы. | Пользователь Б запрашивает жалобу А по её ID и вызывает маршрут принятия решения: оба запроса отклонены, данные чужой жалобы не раскрыты, статус жалобы и материала не изменён. А видит свою жалобу; модератор может выполнить разрешённое действие. Подмена `user_id`, `role` или `moderator_id` не даёт полномочий. Истёкшая сессия отклоняется, понижение роли действует на следующий запрос; скрытый текст не появляется в каталоге или в ответе владельцу жалобы. | A01; ASVS `v5.0.0-8.2.1`, `v5.0.0-8.2.2`, `v5.0.0-8.3.1` |
| **SR-02** | В режиме, предназначенном для использования вне локальной разработки, диагностический вывод отключён, а служебная документация API доступна только по явно принятому решению команды. | При запуске в таком режиме запрос к `/docs` и `/openapi.json`, если эти маршруты не объявлены публичными, не возвращает схему API; ошибка запроса не раскрывает стек вызовов или параметры конфигурации. | A02; ASVS `v5.0.0-13.4.2`, `v5.0.0-13.4.5` |
| **SR-03** | Состав сторонних библиотек и разрешённые источники их получения зафиксированы; известные уязвимости зависимостей рассматриваются до использования версии в сборке. | Для сборки доступен список библиотек с версиями и источниками. Сборка из подменённого источника либо с версией, нарушающей срок устранения уязвимости, указанный ниже, не принимается. | A03; ASVS `v5.0.0-15.1.1`, `v5.0.0-15.1.2`, `v5.0.0-15.2.1` |
| **SR-04** | Пароли учебных аккаунтов в хранилище представлены стойкими адаптивными хешами; открытые пароли не входят в исходный код, файл начальных данных, ответы API и журналы. | При осмотре файла SQLite и данных для развёртывания пароль модератора в открытом виде отсутствует. Хеш содержит параметры Argon2id не ниже выбранных в D-01; простой быстрый хеш не принимается. Вход с верным паролем проходит при отсутствии блокировки, с неверным — отклоняется; пароль и хеш не появляются в ответах и журналах. Сессионный токен выдаётся только в успешном ответе входа и отсутствует в остальных ответах и журналах. | A04; ASVS `v5.0.0-11.4.2`, `v5.0.0-16.2.5`, `v5.0.0-15.3.1` |
| **SR-05** | Любой клиентский ввод, участвующий в выборе или изменении записей, передаётся в запрос к БД как данные, без изменения структуры запроса. Допустимые поля, длины, перечисления и размер выдачи ограничены сервером согласно D-03; недопустимый запрос не меняет данные. | Причина жалобы или параметр запроса с SQL-метасимволами сохраняется или отвергается по правилам поля; чужие жалобы не возвращаются, другие записи и схема БД не изменяются. | A05; ASVS `v5.0.0-1.2.4` |
| **SR-06** <a id="sr-06"></a> | Жалоба может перейти из ожидания только в одно окончательное состояние. Запись единственного решения, изменение статуса, аудит решения и, при удовлетворении жалобы, скрытие материала составляют одну атомарную операцию. Отклонение жалобы не меняет видимость материала. Другие жалобы на тот же материал рассматриваются независимо, но ни одна не восстанавливает уже скрытый материал. | Два одновременных решения по одной жалобе приводят ровно к одному сохранённому решению; после получения блокировки второй запрос получает `409` без изменения предметных данных. При истечении ожидания блокировки допустим безопасный `503`; повтор после завершения первого запроса даёт `409`. Отдельное событие отказа в аудите не считается предметным изменением. Если две разные жалобы одного материала удовлетворяют и отклоняют в любом порядке или одновременно, оба решения сохраняются, материал остаётся `hidden`. Повторное решение по окончательной жалобе отклонено. | A06; ASVS `v5.0.0-2.3.3`, `v5.0.0-15.4.2` |
| **SR-07** | Вход в аккаунты, включая модераторский, защищён от перебора пароля. После пяти неуспешных попыток за 15 минут аккаунт блокируется на 15 минут с момента пятой ошибки; проверка и изменение счётчика атомарны. Успешный пароль во время блокировки не обходит её. Правило одинаково для существующих и неизвестных логинов. | Первые четыре неверных входа дают общий отказ; пятая ошибка включает ограничение. Последующие попытки, включая верный пароль, блокируются до конца периода; после него верный пароль принимается. Параллельные попытки и перезапуск сервера не сбрасывают лимит; успешные и неуспешные входы наблюдаемы в журнале без паролей. | A07; ASVS `v5.0.0-6.1.1`, `v5.0.0-6.3.1`, `v5.0.0-16.3.1` |
| **SR-08** | Начальное заполнение использует только встроенный версионируемый учебный каталог с допустимыми статусами; оно атомарно и при повторном запуске не заменяет существующие записи, роли или состояние материала. Внешний импорт начальных данных не разрешён. | В чистой БД появляется полный начальный каталог. Недопустимый статус или искусственная ошибка между вставками откатывают все новые записи. Повторное заполнение после скрытия материала сохраняет `hidden`, количество и содержимое существующих записей не меняются. | A08; собственное требование жизненного цикла начальных данных; ASVS `v5.0.0-14.1.1`, `v5.0.0-14.1.2` — классификация и выбор защиты. Криптографическая целостность внешнего файла по `14.2.4` не заявляется: такого входа нет. |
| **SR-09** | Приложение фиксирует решения модератора и неуспешные попытки доступа с исполнителем, объектом, временем и результатом; записи защищены от изменения через обычные маршруты API. Исполнитель и время задаются сервером; аудит успешного решения сохраняется в той же транзакции, а отказы — отдельной записью после отката. Локальный оператор просматривает таблицу аудита через SQLite; текст жалобы, пароли, хеши и токены в неё не включаются. | После принятия или отклонения жалобы доступна запись с ID модератора, ID жалобы, временем и результатом. После отказа в чужом запросе видна запись отказа без текста чужой жалобы. Пользователь не может изменить эти записи через API. Успешные и неуспешные входы также оставляют события; незафиксированное решение не оставляет события успеха. | A09; ASVS `v5.0.0-16.2.1`, `v5.0.0-16.3.1`, `v5.0.0-16.3.2`, `v5.0.0-16.3.3`, `v5.0.0-16.4.2` |
| **SR-10** | При ошибке записи решения, статуса жалобы или состояния материала операция целиком отменяется; клиент получает безопасный ответ об ошибке без внутренних деталей. | Искусственная ошибка БД между шагами рассмотрения возвращает отказ. В БД остаются исходные статус жалобы и состояние материала, нового решения нет; ответ не содержит SQL-запроса, трассировки или секрета. | A10; ASVS `v5.0.0-2.3.3`, `v5.0.0-16.5.1`, `v5.0.0-16.5.3` |

## Границы и дальнейшая проверка

- Все SR относятся к целевому продукту. В версии S05 реализована только запускаемая основа: каталог, инициализация, ограниченная выдача и безопасные ошибки. [Фактические проверки](PROJECT.md#run) подтверждают только этот объём; аутентификация, модерация и весь набор критериев ещё не реализованы и не проверены.
- Приоритетные цепочки и остаточные ограничения находятся в [модели угроз](THREAT_MODEL.md) и [D-01–D-03](DESIGN_DECISIONS.md). Идентификаторы исходных SR сохранены.
- `SR-02`: продукт запускается на `127.0.0.1`; публичное развёртывание не запланировано. Отладочные traceback отключены всегда; документация включается только явным локальным параметром. Это не замена контроля доступа.
- `SR-03`: разрешённый источник Python-пакетов — `https://pypi.org/simple` и его хранилище `files.pythonhosted.org`, версии фиксируются вместе с кодом. До принятия сборки проверяются сообщения об уязвимостях применимых версий; подтверждённая критическая/высокая уязвимость, затрагивающая используемый путь, блокирует сборку до исправления. Для остальных применимых уязвимостей назначается исправление не позднее 30 дней после обнаружения. Отсутствие такого анализа не означает «уязвимостей нет». Автоматизированный SCA не является требованием EK1.
- `SR-08`: исходная условная формулировка про внешний seed-файл уточнена после выбора архитектуры. Каталог — публичные учебные данные; аккаунты, жалобы, решения и аудит требуют контроля записи. Локальный оператор и проверенный исходный код входят в доверенную базу. Изменение доверенного кода или SQLite владельцем машины не предотвращается самим API.
- Доступность локального процесса и диска ограничена ресурсами машины. Блокировка входа может использоваться для отказа в обслуживании аккаунта; ограничения и пересмотр решения описаны в D-01.
