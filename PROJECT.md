## 1. Назначение

Продукт представляет собой веб-API для обработки жалоб пользователей на материалы из заранее подготовленного учебного каталога.

Пользователь может просматривать доступные материалы, отправлять жалобу на выбранный материал и отслеживать состояние своих обращений. Модератор рассматривает поступившие жалобы, принимает решение и указывает его причину.

Собственная предметная логика приложения заключается в управлении жизненным циклом жалобы и изменении состояния материала в зависимости от решения модератора.

## 2. Граница продукта

**В продукт входит:**

- хранение заранее подготовленного каталога учебных материалов;
- получение списка доступных материалов;
- создание пользователем жалобы на материал;
- хранение причины жалобы;
- просмотр пользователем собственных жалоб и их состояния;
- просмотр модератором жалоб, ожидающих рассмотрения;
- принятие или отклонение жалобы модератором;
- фиксация причины решения модератора;
- скрытие материала при удовлетворении жалобы;
- разграничение возможностей пользователя и модератора;
- хранение состояния материалов, жалоб и решений.

**Внешнее окружение и внешние системы:**

- HTTP-клиент, взаимодействующий с REST API приложения, например `curl`, Postman или аналогичный инструмент;
- локальное окружение, в котором запускаются сервер и база данных.

Внешние информационные системы и сторонние API для работы основных сценариев не требуются.

**Команда сознательно не реализует:**

- отдельный веб-интерфейс или мобильное приложение;
- регистрацию новых пользователей;
- загрузку пользовательских материалов;
- редактирование пользователями содержимого материалов;
- систему апелляций на решения модераторов;
- автоматическую модерацию содержимого;
- уведомления по электронной почте, SMS или другим внешним каналам;
- интеграции со сторонними сервисами;
- расширенную аналитику и статистику модерации.

Для проверки продукта используются заранее созданные учебные аккаунты и учебные данные.

## 4. Сквозные сценарии

### Сценарий 1. Отправка жалобы на материал

- **Участники:** пользователь.
- **Начальное условие:** пользователь имеет доступ к системе; материал существует и доступен для просмотра.
- **Основные действия:**
  1. Пользователь получает список доступных материалов.
  2. Выбирает материал, который считает спорным.
  3. Отправляет жалобу и указывает её причину.
  4. Система проверяет существование материала и корректность данных жалобы.
  5. Система создаёт жалобу со статусом ожидания рассмотрения.
- **Результат:** жалоба зарегистрирована и доступна для последующего рассмотрения модератором.
- **Какие данные или состояние изменяются:** создаётся новая жалоба, сохраняются её автор, материал, причина, время создания и статус.

### Сценарий 2. Рассмотрение жалобы модератором

- **Участники:** модератор.
- **Начальное условие:** существует жалоба, ожидающая рассмотрения.
- **Основные действия:**
  1. Модератор получает список необработанных жалоб.
  2. Открывает конкретную жалобу и связанный с ней материал.
  3. Выбирает решение: удовлетворить жалобу или отклонить её.
  4. Указывает причину принятого решения.
  5. Система сохраняет решение.
  6. При удовлетворении жалобы система переводит материал в скрытое состояние; отклонение жалобы не меняет видимость материала.
  7. Статус жалобы, единственное решение, изменение материала и запись аудита сохраняются атомарно. Повторное или конкурирующее решение той же жалобы отклоняется.
- **Результат:** жалоба получает окончательный статус и зафиксированное решение модератора.
- **Какие данные или состояние изменяются:** изменяются статус жалобы и данные о решении; при удовлетворении жалобы изменяется состояние материала.

У одного материала может быть несколько жалоб. Удовлетворение любой из них оставляет материал скрытым: отклонение другой жалобы его не восстанавливает. Оставшиеся жалобы можно рассмотреть, а модератору доступен скрытый материал. Пользователь видит результат собственной жалобы, но не текст скрытого материала. Операции восстановления в границе продукта нет.

### Сценарий 3. Просмотр результата своей жалобы

- **Участники:** пользователь.
- **Начальное условие:** пользователь ранее отправил хотя бы одну жалобу.
- **Основные действия:**
  1. Пользователь запрашивает список своих жалоб.
  2. Система выбирает только жалобы, созданные данным пользователем.
  3. Пользователь получает текущее состояние каждой жалобы.
  4. Для рассмотренной жалобы пользователь видит итоговое решение и его причину.
- **Результат:** пользователь может узнать, рассмотрено ли его обращение и какое решение по нему принято.
- **Какие данные или состояние изменяются:** состояние системы не изменяется; выполняется чтение актуального состояния жалоб и решений.

## 6. Компоненты и внешние взаимодействия

Предполагаемые компоненты продукта:

1. **REST API сервер**
   - принимает HTTP-запросы пользователей и модераторов;
   - выполняет проверку входных данных;
   - проверяет полномочия пользователя;
   - реализует предметную логику работы с материалами и жалобами;
   - возвращает результаты в формате JSON.

2. **Хранилище данных**
   - хранит учебные аккаунты;
   - хранит каталог материалов;
   - хранит жалобы;
   - хранит решения модераторов и состояния материалов.

3. **API-клиент**
   - отдельный frontend не реализуется;
   - для взаимодействия с API могут использоваться `curl`, Postman, Swagger UI.

Единый актуальный архитектурный вид, потоки, планируемые точки входа и границы доверия находятся в [модели угроз](THREAT_MODEL.md#architecture). Компоненты выше описывают целевую архитектуру; наличие описания не означает наличие кода.

В целевом API сервер устанавливает личность по проверенным учётным данным и серверной сессии, получает роль из БД и проверяет право на объект. Переданные клиентом `user_id`, `role`, `moderator_id` не являются основанием полномочий. Подробности и ограничения — в [D-01](DESIGN_DECISIONS.md#d-01).

Работа основных сценариев не зависит от внешних интернет-сервисов. HTTP допускается только на loopback в учебном окружении; публичное развёртывание и настройка TLS сейчас не входят в проект.

## 9. Стек и путь к первой работающей версии

**Основные технологии:**

- Python 3.11 и новее;
- FastAPI — реализация REST API;
- Pydantic — описание и проверка входных и выходных данных;
- SQLAlchemy — работа с данными;
- SQLite — локальная база данных;
- Uvicorn — запуск ASGI-приложения;

**Технологии, новые для команды:** Pydantic и SQLAlchemy.

**Внешние сервисы, необходимые для запуска:** отсутствуют.

**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:** все основные сценарии выполняются локально. Сервер и SQLite-база запускаются на компьютере разработчика, а API проверяется с помощью HTTP-запросов. Доступ к внешним сервисам и сети для работы предметных сценариев не требуется.

**Минимальная запускаемая основа (S05):**

- `app/main.py` — FastAPI-приложение: `GET /health` выполняет реальное чтение SQLite, `GET /materials` отдаёт только материалы в состоянии `visible`;
- `app/models.py` — начальная схема: пользователи, материалы, жалобы, решения и события аудита с ограничениями допустимых значений, внешними ключами и `UNIQUE` на решение по жалобе (основа D-02);
- `app/seed.py` — встроенный учебный каталог из трёх синтетических материалов; заполнение выполняется одной транзакцией и добавляет только отсутствующие записи (SR-08);
- `tests/test_foundation.py` — автоматизированные проверки реализованного объёма.

Начальный каталог задаётся константами в версионируемом коде, отдельного импортируемого файла нет. Учебные аккаунты будут создаваться отдельной локальной командой с вводом пароля без эха: в репозиторий и seed открытые пароли не попадают. Таблицы жалоб, решений и аудита пока пусты: маршрутов, изменяющих данные, нет.

Следующие этапы: учебные аккаунты и вход по D-01, затем создание жалобы, получение собственных жалоб и рассмотрение модератором по D-02. Схема создаётся через `create_all` и не является системой миграций: при изменении существующих таблиц потребуется отдельное решение о миграции данных.

## 10. Запуск и проверка минимальной основы

**Окружение:** Python 3.11 или новее, `venv`, доступ к PyPI для первоначальной установки зависимостей. После установки сервер работает без внешних сервисов. Запускается один процесс Uvicorn на loopback; база — локальный файл SQLite.

**Установка и запуск из корня репозитория (macOS/Linux):**

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

В Windows окружение создаётся командой `py -m venv .venv`, активируется `.venv\Scripts\activate`.

При первом старте создаются каталог `data/` и файл `data/app.sqlite3` с тремя видимыми учебными материалами. Учётных записей, жалоб и решений не создаётся. Повторный запуск добавляет только отсутствующие материалы и не меняет существующие строки, в том числе скрытые. Если заполнение каталога завершилось ошибкой, все его вставки откатываются; сервер продолжает запуск, а `/health` показывает состояние БД.

Путь к базе задаётся переменной `DATABASE_PATH`, например `DATABASE_PATH=data/demo.sqlite3` для чистой демонстрации. Каталог `data/`, файлы `*.sqlite3`, `.venv/` и `.env` исключены из Git.

**Проверка во втором терминале:**

```bash
curl -i http://127.0.0.1:8000/health
curl -s http://127.0.0.1:8000/materials
curl -s 'http://127.0.0.1:8000/materials?limit=1&offset=1'
curl -i 'http://127.0.0.1:8000/materials?limit=101'
curl -i http://127.0.0.1:8000/openapi.json
```

| Запрос | Ожидаемый результат |
| --- | --- |
| `GET /health` | `200`, `{"status":"ok","database":"ok"}`. При недоступной БД — `503` без деталей SQLite. |
| `GET /materials` | `200`, JSON-массив из трёх материалов с полями `id`, `title`, `body`. Скрытые материалы не выдаются. |
| `GET /materials?limit=1&offset=1` | Один материал — второй из видимых в порядке `id`. Скрытые отфильтровываются до пагинации. |
| `GET /materials?limit=101` | `422`, `{"detail":"Invalid request"}`; входное значение в ответ не попадает. |
| `GET /openapi.json` | `404`: документация выключена по умолчанию. |

Параметры списка: `limit` от 1 до 100 (по умолчанию 20), `offset` от 0 до 9223372036854775807. Любые другие параметры (`sort`, `filter` и т. п.) отклоняются с `422`.

Для локальной разработки документацию можно включить: `ENABLE_API_DOCS=1 python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`, затем открыть `http://127.0.0.1:8000/docs`. Остановка сервера — `Ctrl+C`, данные сохраняются в файле.

**Автоматизированные проверки:**

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m pip check
```

[tests/test_foundation.py](tests/test_foundation.py) проверяет: заполнение свежей БД; сохранение `hidden` и отсутствие дублей при перезапуске; фильтрацию скрытых материалов до пагинации; отклонение недопустимых и лишних параметров без отражения ввода; выключенную по умолчанию и явно включаемую документацию; отсутствие маршрутов жалоб; полный откат неудачного заполнения; ограничения схемы, внешние ключи и единственность решения по жалобе; безопасный `503` при повреждённой схеме.
