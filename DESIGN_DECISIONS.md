# Проектные решения безопасности

Проект: **«Разбор жалоб на контент»**. Основания: [паспорт](PROJECT.md), [требования SR-*](SECURITY_REQUIREMENTS.md), [модель угроз T-*](THREAT_MODEL.md).

**Статус S04:** ниже зафиксированы решения для будущей реализации. Сценарии проверки задают условия и ожидаемый результат; они не являются выполненными тестами или свидетельствами безопасности. При реализации сохраняются ID решений, а фактический результат проверки связывается с конкретной версией продукта.

Приоритетный набор покрывается следующими связями: T-01/T-02 → SR-01/SR-04/SR-07 → D-01; T-03/T-04 → SR-06/SR-09/SR-10 → D-02; T-05 → SR-05 → D-03. Дополнительные связи внутри решений указывают на конкретную ограничиваемую часть угрозы, а не на полное устранение всех рисков.

<a id="d-01"></a>
## D-01. Доверенный контекст входа и проверка права на каждый объект

**Контекст.** Клиент полностью контролирует URL, JSON и заголовки запроса. Идентификатор жалобы не подтверждает право читать её, а переданные `author_id`, `moderator_id` или `role` не подтверждают личность и полномочия. Компрометация аккаунта модератора открывает доступ ко всем жалобам и скрытию материалов.

**Решение.**

1. Учебные аккаунты создаются командой при локальной инициализации. Пароли поступают вне репозитория; в БД сохраняются только адаптивные хеши Argon2id с индивидуальной случайной солью не менее 16 байт. Начальные параметры: память 65 536 КиБ, три прохода, параллелизм 1, хеш 32 байта. Это выбранная базовая конфигурация проекта; её стоимость проверяется на учебной машине до ввода механизма в работу, а ослабление требует отдельного обоснованного пересмотра. Параметры включаются в сохранённый хеш; журналирование входного пароля запрещено.
2. После успешного входа сервер выдаёт непрозрачный токен из 32 криптографически случайных байтов. Клиент передаёт его в `Authorization: Bearer …`. В таблице сессий сохраняются SHA-256-отпечаток токена, `user_id` и абсолютное время истечения через один час. Токен не содержит утверждения о роли; его передача в URL не поддерживается. Отпечаток подходит для случайного токена высокой энтропии и не заменяет Argon2id для пароля.
3. Для каждого защищённого запроса сервер проверяет сессию, срок действия и существование аккаунта, затем читает актуальную роль из БД. Отсутствующая, неизвестная или истёкшая сессия даёт `401`. Изменение роли не требует ожидать истечения старого токена: следующий запрос использует новые полномочия.
4. Сервер получает автора новой жалобы и исполнителя решения только из этого контекста. Список жалоб обычного пользователя фильтруется по его `user_id` на сервере; чтение отдельной жалобы проверяет владельца. Чужая и несуществующая жалобы для обычного пользователя дают одинаковый `404` без её полей. Модераторские операции проверяют роль и при её отсутствии дают `403` без изменений. Поля назначения автора, исполнителя, времени или роли в клиентском теле не допускаются схемой D-03.
5. Для входа действует единое правило по нормализованному логину: пять неверных попыток в течение 15 минут блокируют дальнейший вход на 15 минут после пятой ошибки. Верный пароль во время блокировки не обходит её. Счётчики и время блокировки хранятся в SQLite; проверка ограничения, изменение счётчика и разрешение выдачи сессии согласуются атомарно. Одновременные запросы и перезапуск процесса не сбрасывают защиту. Для неизвестного логина действуют те же правило, общий текст ошибки и ограничение; успешный вход вне блокировки сбрасывает счётчик. Формат и нормализация логина одинаковы при создании аккаунта и входе.

**Обоснование.** Серверная сессия связывает запрос с аккаунтом, а актуальная роль и принадлежность объекта задают допустимое действие. Проверка выполняется и для прямого HTTP-запроса, и для запроса из Swagger UI. Непредсказуемость ID жалобы не используется как защита. Хранение счётчиков в БД делает лимит общим для процессов, использующих эту БД; Argon2id затрудняет подбор по утёкшему хешу, а ограничение входа — подбор через API.

**Альтернатива и условие пересмотра.** Подписанный токен с ролью уменьшил бы число чтений сессии, но роль могла бы устареть до истечения токена; немедленный отзыв потребовал бы дополнительного состояния. Для локального API с одной SQLite-базой выбраны серверные сессии. Выбор пересматривается при появлении внешнего поставщика идентичности или нескольких независимо развёрнутых сервисов с явными требованиями к отзыву и актуальности полномочий.

**Предположения.** Все маршруты чтения жалоб и изменения состояния используют общий серверный контекст. SQLite и часы локального сервера доступны; серверное время используется для сроков, клиент его не задаёт. Учебный запуск слушает loopback; выход за эту границу потребует защищённого транспорта и пересмотра модели. Локальный пользователь с правом прямого изменения файла БД находится вне защиты HTTP-авторизации.

**Связанные угрозы:** [T-01](THREAT_MODEL.md#t-01), [T-02](THREAT_MODEL.md#t-02); [T-06](THREAT_MODEL.md#t-06) в части хранения паролей и сессий.

**Связанные требования:** SR-01, SR-04, SR-07; SR-09 для регистрации входов и отказов по D-03.

**Будущая проверка.**

| Условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |
| Есть пользователи А, Б, модератор и жалоба А. | От имени Б напрямую запросить список и ID жалобы А; вызвать принятие решения; затем выполнить разрешённые запросы А и модератора. | В списке Б нет жалобы А; чужой ID даёт тот же `404`, что отсутствующий; принятие решения Б даёт `403`. После отказов предметные данные не меняются, отдельное событие отказа появляется в аудите. А видит свою жалобу, модератор выполняет допустимое действие. |
| У Б действующая сессия. | Передать чужие `author_id`, `moderator_id` или `role` в теле создания жалобы/решения. | Недопустимые поля отклонены; чужой автор или исполнитель не записан. Корректный запрос создания сохраняет Б как автора. |
| Выдан токен модератора. | Завершить тестовую смену его роли в БД на обычную, затем с прежним токеном вызвать модераторскую операцию. Отдельно повторить запрос после истечения сессии. | В первом случае `403` без изменения жалобы, во втором `401`. Роль из прежнего контекста не используется. |
| Для существующего и неизвестного логина нет ошибок входа. В тесте управляется серверное время. | Выполнить пять неверных попыток, в том числе конкурентно; затем попробовать верный пароль, перезапустить процесс и повторить. Продвинуть время за срок блокировки. | Во время блокировки вход ограничен и после перезапуска; известный аккаунт не получает сессию даже с верным паролем. После истечения ограничения верный пароль работает. Неизвестный логин получает тот же класс ответов и правило ограничения. |
| Созданы аккаунт и действующая сессия. | Осмотреть БД, исходные начальные данные, ответы ошибок и журналы; повторить вход с верным и неверным паролем. | В БД есть Argon2id-хеш и отпечаток токена; открытого пароля и полного токена в перечисленных артефактах нет. Верный пароль вне блокировки работает, неверный не даёт сессию. |

**Ограничения и последствия.** Украденный действующий токен позволяет действовать до его истечения или удаления сессии; защита устройства клиента не входит в это решение. Лимит по аккаунту допускает временную блокировку жертвы злоумышленником и не заменяет защиту от распределённой нагрузки. Для неизвестных логинов нужны ограниченный срок хранения и очистка устаревших счётчиков. Одинаковые ответы не объявляются доказательством отсутствия всех временных побочных каналов. Параметры Argon2id и токены добавляют вычислительные и эксплуатационные обязанности, которые проверяются при реализации.

<a id="d-02"></a>
## D-02. Единственное окончательное решение и согласованное состояние материала

**Контекст.** Между чтением статуса `pending` и записью решения может прийти второй запрос. Между отдельными записями решения, жалобы, материала и журнала может возникнуть сбой. Кроме того, несколько разных жалоб могут относиться к одному материалу: корректность одной жалобы не гарантирует корректность общего материала.

**Решение.**

1. Рассмотрение выполняется одним серверным сервисом. После проверки формата запроса он открывает транзакцию SQLite через `BEGIN IMMEDIATE` **до чтения изменяемого состояния**. Внутри повторно читает актуального исполнителя и роль, жалобу и связанный материал. Это исключает использование предварительно прочитанного статуса как основания записи.
2. Переход жалобы допускается только из `pending` в `accepted` или `rejected`. На `complaint_id` в таблице решений действует `UNIQUE`, на ссылки — внешние ключи, на роли и статусы — ограничения допустимых значений. Внешние ключи включаются для каждого SQLite-соединения. Повторное решение по завершённой жалобе возвращает `409`, сохраняя первое решение.
3. Решение содержит ID жалобы, ID исполнителя из доверенного контекста, результат, обязательную причину и серверное время. Запись решения, окончательного статуса жалобы и события аудита составляют одну транзакцию. При `accepted` в эту же транзакцию входит переход материала `visible → hidden`. При `rejected` состояние материала вообще не изменяется. Обратного перехода `hidden → visible` в текущей границе продукта нет.
4. Модератору доступен связанный материал и после скрытия, чтобы рассмотреть оставшиеся жалобы. Обычный пользователь видит результат своей жалобы без получения скрытого содержимого через вложенный объект ответа. Этот путь чтения подчиняется D-01 и схеме ответа D-03.
5. Любая ошибка до успешного `COMMIT`, в том числе отказ записи аудита, приводит к `ROLLBACK` всей операции. Окончательный успешный ответ отправляется только после фиксации. Конфликт блокировки обрабатывается как временная недоступность безопасным ответом; приложение не продолжает запись без блокировки и не повторяет автоматически часть операции.

**Обоснование.** Ранняя блокировка писателя сериализует конкурентные изменения в одной SQLite-базе; второй обработчик читает уже зафиксированный статус. Уникальность решения дополнительно защищает инвариант на уровне БД. Общая транзакция не оставляет жалобу без решения или материал без связанного результата и аудита. Отсутствие операции восстановления делает скрытие монотонным и при разных жалобах на один материал.

**Альтернатива и условие пересмотра.** Применим условный `UPDATE … WHERE status = 'pending'` с проверкой `rowcount = 1`, записью решения и изменением материала в одной транзакции. Он может быть удобнее в СУБД с конкуренцией по строкам, но простое чтение с последующей безусловной записью таким вариантом не является. Для маленького локального SQLite-продукта выбрана ранняя блокировка писателя: порядок проще объяснить и проверить. Цена — сериализация всех записей и возможное ожидание даже для разных жалоб. При измеренной нехватке пропускной способности или переходе на другую СУБД решение пересматривается с сохранением предметных инвариантов и конкурентных проверок.

**Контрпример, уточнивший решение.** Недостаточное предположение: «если решение по каждой жалобе атомарно, материал всегда согласован». Пусть жалобы X и Y относятся к одному материалу. Модератор удовлетворяет X и скрывает материал, а затем другой модератор отклоняет Y. Реализация «при отклонении сделать материал видимым» отменит действие X, хотя обе транзакции по отдельности корректны. Поэтому в T-03 включён путь через разные жалобы, в SR-06 уточнено отсутствие восстановления, а D-02 различает переход `accepted` и отсутствие изменения материала при `rejected`. Будущая проверка охватывает оба порядка и конкурентное выполнение X/Y.

**Предположения.** Все изменения жалоб, решений и видимости проходят через этот сервис; обычный API не имеет маршрута восстановления материала или редактирования решения. Все процессы используют один и тот же локальный файл SQLite с рабочими блокировками. Прямые правки БД оператором вне API не защищаются этой транзакцией.

**Связанные угрозы:** [T-03](THREAT_MODEL.md#t-03), [T-04](THREAT_MODEL.md#t-04); [T-10](THREAT_MODEL.md#t-10) в части согласованной фиксации решения и аудита.

**Связанные требования:** SR-06, SR-09, SR-10; SR-01 для исполнителя и доступа к объектам.

**Будущая проверка.**

| Условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |
| Одна жалоба `pending`, два модератора, отдельные соединения к одной файловой БД. | Одновременно начать принятие и отклонение одной жалобы. После завершения обоих запросов повторить рассмотрение. | Ровно одно решение и соответствующее событие аудита сохранены. Проигравший запрос получает `409` после чтения актуального состояния либо безопасный временный отказ при истечении ожидания блокировки; повтор после завершения всегда даёт `409`. Итоговые статус и видимость соответствуют победившему решению. |
| Две жалобы X/Y на один видимый материал. | Удовлетворить X и отклонить Y в обоих последовательных порядках, затем повторить на свежих данных конкурентно через разные соединения. | Обе жалобы имеют свои решения; материал остаётся `hidden` после любого успешно зафиксированного удовлетворения. Отклонение Y не восстанавливает видимость. В случае временного отказа конкурентный запрос повторяется целиком после снятия блокировки. |
| Жалоба `pending`; исходное состояние БД сохранено для сравнения. | Внедрить ошибку после каждого шага записи, отдельно при записи аудита и при фиксации, затем выполнить `accepted`. | Ответ безопасен, в БД нет нового решения или события успешной модерации, статус жалобы и материал остаются исходными. После устранения сбоя допустимая операция завершается целиком. |
| Материал уже скрыт решением по X, Y ещё ожидает рассмотрения. | Модератор читает Y и связанный материал; обычный автор Y читает свою жалобу. | Модератор получает данные для рассмотрения. Автор видит свою жалобу и её состояние, но не получает скрытый текст материала через этот путь. |
| В таблице решений уже есть запись; ограничения БД включены. | Попробовать в тесте создать второе решение на тот же `complaint_id`, недопустимый статус и ссылку на отсутствующий объект. | БД отклоняет операции; предыдущее состояние остаётся целым. Эта проверка дополняет, а не заменяет конкурентный HTTP-сценарий. |

**Ограничения и последствия.** Потеря ответа после успешного `COMMIT` не означает откат: повтор даст `409`, а клиент выясняет итог чтением жалобы. Решение не обеспечивает идемпотентное повторение ответа по ключу запроса и не обещает доступность при длительной блокировке файла. Добавление апелляций или восстановления видимости потребует новой предметной модели и пересмотра SR-06, T-03 и этого решения. Встроенная транзакция не заменяет резервное копирование и не защищает от оператора с правом изменять файл БД.

<a id="d-03"></a>
## D-03. Ограниченные входы, параметризованные запросы и безопасная диагностика

**Контекст.** Причина жалобы и решения — недоверенный текст. Параметры URL и тела могут содержать SQL-фрагменты, дополнительные поля или недопустимые значения. Даже отклонённый запрос способен раскрыть секрет через стандартную подробную ошибку валидации или журнал исходного тела.

**Решение.**

1. Каждая изменяющая операция имеет отдельную Pydantic-схему разрешённых полей с запретом лишних полей. Клиент создаёт жалобу только из `material_id` и `reason`, а решение — из результата и `reason`. ID — положительные целые; результат — только `accepted` или `rejected`. Причина после удаления краевых пробелов содержит от 1 до 2000 символов. Поля автора, исполнителя, роли, времени и текущего статуса сервер назначает сам.
2. SQLAlchemy передаёт клиентские значения как связанные параметры. Конкатенация клиентского ввода в SQL и выбор SQL-выражения из строки пользователя запрещены. Списки используют заданный сервером порядок по ID, `limit` по умолчанию 20, максимум 100, и неотрицательный `offset`; произвольные `sort` и `filter` не поддерживаются. Синтаксически допустимый SQL-подобный текст в причине остаётся обычным текстом, а не запрещается по списку SQL-слов.
3. Ответы формируются по явным схемам разрешённых полей, а не сериализацией всей ORM-записи. Хеш пароля, отпечаток сессии и внутренние настройки не включаются в ответы. Скрытый текст материала не вкладывается в обычный пользовательский ответ о жалобе. Ограничение выдачи не заменяет проверку владельца и роли из D-01.
4. Обработчики ошибок возвращают стабильный код и безопасное сообщение. Ошибки валидации не отражают исходное тело, пароль, токен или внутреннюю структуру исключения. Ошибки БД не раскрывают SQL, параметры или трассировку. `/docs` и `/openapi.json` по умолчанию выключены; для локальной разработки команда включает их явным параметром. Отладочный вывод клиенту отключён. Публичное развёртывание сейчас не проектируется: выход за loopback потребует пересмотра конфигурации и модели.
5. События решения, успешного и неуспешного входа, отказа доступа получают тип, время сервера, результат, ID установленного исполнителя и ID объекта, если они известны. События не содержат пароль, Bearer-токен, хеш, тело запроса или текст чужой жалобы. Аудит успешного решения фиксируется в транзакции D-02; отказ доступа или предметной операции записывается отдельно после её отката, без события успеха. Обычный HTTP API не предоставляет изменение или удаление журнала. Команда просматривает журнал локально через SQLite с правами на файл БД; недоступность записи аудита не превращает отказ в разрешение операции.

**Обоснование.** Схема запроса определяет полномочия клиентского ввода, связанные параметры отделяют данные от структуры SQL, а схема ответа ограничивает раскрываемые поля. Валидация формата без параметризации не защищает текстовые поля от инъекции. Доступный для локального просмотра минимальный аудит позволяет связать действие с исполнителем без копирования секретов в ещё одно хранилище.

**Альтернатива и условие пересмотра.** Фильтрация строк по «опасным словам» проста, но запрещает допустимый текст и не даёт гарантии неизменности SQL. Универсальный конструктор фильтров с широкими ответами добавил бы пути обхода без необходимости для трёх основных сценариев. Выбраны фиксированные схемы, порядок выдачи и параметры. При добавлении поиска или экспорта новые поля и пути выдачи сначала включаются в SR-01/SR-05, модель потоков и будущие проверки.

**Предположения.** Все запросы проходят через те же схемы и слой доступа к данным; служебные операции также не строят SQL из недоверенных строк. Доступ к локальному журналу имеет оператор учебного окружения. Сбой журналирования наблюдаем оператором через безопасное служебное сообщение, не содержащее входные данные или секреты.

**Связанные угрозы:** [T-05](THREAT_MODEL.md#t-05); [T-06](THREAT_MODEL.md#t-06) в части утечки через ответы и журналы; [T-09](THREAT_MODEL.md#t-09), [T-10](THREAT_MODEL.md#t-10).

**Связанные требования:** SR-05, SR-09, SR-10; SR-01 для разрешённых полей; SR-04 для отсутствия паролей в ответах и журналах; SR-02 для конфигурации документации и диагностики.

**Будущая проверка.**

| Условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |
| У А и Б есть разные жалобы; схема и число записей БД известны. | Отправить причины с кавычками и SQL-фрагментами, например `x'); DROP TABLE complaints; --`; повторить с недопустимым строковым ID и дополнительным полем `role`. | Допустимый текст сохраняется как данные; некорректный ID и лишнее поле отклонены. Схема и посторонние записи не изменены, чужие жалобы не возвращены. Нормальное создание жалобы продолжает работать. |
| У пользователя более 100 собственных жалоб. | Запросить выдачу без лимита, с `limit=100`, `limit=101`, отрицательным `offset`, произвольным `sort`; отправить пустую, пробельную и слишком длинную причину. | Без лимита возвращается не более 20 записей; допустимый лимит действует, недопустимые параметры и причины отклонены. Порядок стабилен; ошибка не содержит исходного текста поля. |
| Запрос содержит тестовые пароль и токен с узнаваемыми маркерами. | Спровоцировать ошибку входа, валидации и БД; просмотреть ответы, stdout/stderr и аудит. | Маркеры не появляются в ошибках и журналах; SQL, трассировка и настройки отсутствуют в клиентском ответе. БД после ошибки записи соответствует D-02. |
| Есть успешное решение и отказ Б при попытке чтения жалобы А. Выполнены успешный и неуспешный входы. | Прочитать аудит через SQLite и попытаться изменить его обычным HTTP-запросом пользователя. | Для действий видны исполнитель/объект/время/результат, если они установлены; для входов есть события с результатом. Текста чужой жалобы и секретов нет. Маршрут изменения аудита отсутствует. Запись успешного решения соответствует зафиксированной жалобе. |
| Приложение запущено на loopback с настройками по умолчанию, затем с явным включением локальной документации. | Запросить `/docs`, `/openapi.json` и вызвать ошибку приложения. | По умолчанию документация не выдаётся; после явного включения доступна локально. Обе конфигурации не возвращают клиенту секреты и внутреннюю трассировку. |

**Ограничения и последствия.** Ограничение размера поля и одной страницы не защищает от произвольной нагрузки или заполнения диска множеством корректных запросов. SQLite-журнал защищён от обычного API, но не от администратора файла; внешнего неизменяемого хранилища и автоматического оповещения здесь нет. Обязательны будущая проверка фактических исключений фреймворка и просмотр полей логов: настройка `debug=false` сама по себе не доказывает отсутствие утечек.
